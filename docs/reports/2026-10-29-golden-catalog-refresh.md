# 골든셋(`engine/testdata/golden_catalog.json`) 갱신 + 몰별 미해결 이슈 재조사

`wishkit-engine`(on/off 토글 배포)을 잠깐 켜고, VPC 내부에서 골든셋 36개 URL 전체를
`/extract`로 다시 돌려 실제 일치율을 확인했다. 골든셋 자체가 몇 달 전 캡처된 값이라
실가격이 그 사이 바뀌었을 가능성이 높다는 의심에서 시작한 점검이었는데, 그 의심은 맞았고
(§1) 덤으로 기존에 "원인 미조사"로 남아 있던 몰별 이슈 2건의 구체적인 원인도 새로 나왔다
(§2).

## 0. 요약

- 36개 중 완전일치 11개(31%), 가격만 일치 11개(31%), ambiguous(가격 포기) 9개(25%),
  차단 에러 2개(6%).
- 가격 불일치 23건 전부 `price_grounded: true`(AI가 읽은 가격이 실제 페이지 원문에
  리터럴로 있었음 확인) — **환각이 아니라 골든셋 자체가 오래돼서 생긴 불일치**로
  판단, 근거가 확인된 필드(price/name/image 각각 grounded일 때만)만 골든셋에 반영했다.
  21개 상품의 price/name/image 중 일부를 갱신했다(§1).
- ambiguous 9건(KREAM 3/3, 4910 3/3, SSF샵 3/3)은 **골든셋을 안 건드렸다** — AI가
  정직하게 "모르겠다"고 기권한 것이지 골든셋이 틀려서가 아니다. 대신 이번에 처음으로
  **구체적인 원인 단서**가 나왔다(§2) — 특히 4910은 기존 진단("조건부/무조건 가격
  혼동")과 다른, 새로운 원인(인증 벽)일 가능성이 있어 재확인이 필요하다.
- 에이블리 2건은 기존에 이미 진단된 Cloudflare 차단(26-1절)과 동일 — 안 건드림.

## 1. 골든셋 갱신 방법과 범위

VPC 내부에서(Lambda가 실제로 쓰는 것과 같은 보안그룹으로) 한 번 쓰고 지울 Fargate
태스크를 띄워 36개 URL 전체를 `/extract`에 던지고, `compare.py`의 `compare_to_golden`과
같은 비교 로직(가격 완전 일치, 이름 유사도 ≥0.8 또는 포함관계, 이미지 basename/숫자열
일치)으로 지금 골든셋과 비교했다.

**갱신 규칙**(사람이 다시 확인하지 않고 AI 결과를 그대로 믿지 않기 위해, 응답에 같이 오는
`grounding` — "AI가 말한 값이 실제 페이지 원문에 있는지" 확인 결과만 반영):

- `ambiguous: false`이고 `grounding.price_grounded: true`면 → `price` 갱신
- `grounding.name_grounded: true`면 → `name` 갱신
- `grounding.image_grounded: true`면 → `image` 갱신
- `ambiguous: true`(9건)거나 호출 자체가 에러(2건, 에이블리 차단)면 → **안 건드림**

21개 상품에서 1개 이상 필드가 바뀌었다(가격만 11건, 가격+이름+이미지 동시 변경도 다수 —
그 사이 할인·시즌 문구·CDN 이미지 경로가 같이 바뀐 경우들). `brand` 필드는 건드리지
않았다. 상세 변경 내역은 이 커밋의 diff 참고.

**주의**: 이건 사람이 쇼핑몰에 직접 들어가 확인한 "검증된 정답"이 아니라, **AI가 스스로
그라운딩까지 확인한, 오늘 시점의 관측값**이다. `compare_to_golden`이 "정확 일치가 아니라
유사도 기반"이라고 이미 스스로 밝히고 있는 것과 같은 맥락 — 골든셋도 100% 신뢰 가능한
정답지는 아니고, 그라운딩 체크로 거짓/환각 가능성만 최대한 줄인 참고용 기준선이다.

## 2. ambiguous 9건 — 기존 진단 재확인 + 신규 단서

`2026-09-24-fargate-validation.md`가 이미 KREAM·4910을 "ambiguous로 일관되게 실패,
몰별 추출 규칙 미해결 이슈"로 분류해뒀다. 이번에 처음으로 Gemini의 `ambiguity_reason`을
그대로 받아보니 더 구체적인 단서가 나왔다.

### KREAM (3/3) — 스크린샷이 완전히 빈 화면

`ambiguity_reason`: "The provided screenshot is completely blank" (3건 전부 같은 취지).
텍스트 1차 추출이 먼저 ambiguous였다는 뜻이고(스크린샷 폴백은 1차가 ambiguous일 때만
호출됨, main.py 참고), 폴백용 스크린샷마저 흰 화면이었다. `render.py`의 "렌더링 완료
대기" 조건(가격 텍스트 노출 또는 약한 신호 3초 후)이 KREAM 특유의 렌더링 방식(레이지
로딩·캔버스 등)과 안 맞아 화면이 그려지기 전에 스크린샷을 찍었을 가능성 — 기존 "원인
미조사"보다는 구체적이지만, 실제로 어느 지점에서 비는지는 KREAM 페이지를 직접 렌더링
단계별로 찍어봐야 확정할 수 있다(이번 조사 범위 밖).

### 4910 (3/3) — "인증되지 않은 유저" 오류 ⚠️ 기존 진단과 다른 원인일 수 있음

`ambiguity_reason`: "화면을 불러오지 못했어요, 인증되지 않은 유저입니다" /
"unauthorized access" (3건 전부). 기존 진단(`2026-09-19-engine-server-port.md` §25/26-3,
"조건부/무조건 가격 혼동")은 **AI가 계산은 했지만 틀렸다**는 내용이었는데, 이번엔 **페이지
자체가 로그인/인증을 요구하는 에러 화면**을 보여줬다 — 전혀 다른 증상이다. 두 가지 중
하나: (a) 4910이 그 사이 상품 페이지에 로그인 요구를 추가했거나, (b) 우연히 이번
3건에서만 세션/쿠키 문제가 있었거나. **이전 진단을 그대로 믿지 말고 재확인 필요** —
로그인 없이 상품 페이지를 볼 수 있는 몰인지 먼저 확인하는 게 우선.

### SSF샵 (3/3) — 봇 탐지가 아니라 간헐적 렌더링 실패로 보임 (최초 판단 정정)

기존 보고서엔 없던 패턴(2026-09-24 전수 조사엔 SSF샵이 포함 안 됐던 것으로 보임).
`ambiguity_reason`: "Access denied Error 16" 계열(3건 공통). `render.py`는 이걸 차단으로
인식하지 못했다(`render.ok: true`, `blocked: false`).

처음엔 "일반 HTTP 요청(브라우저 아님)은 200인데 Playwright만 막힌다"는 걸 보고 헤드리스
브라우저 신호를 탐지하는 차단이라고 적었는데, **그 뒤 직접 재현해보니 이 결론이 틀렸다**.
같은 VPC에서 `render.render()`(엔진이 실제로 쓰는 함수 그대로)로 SSF샵 3개 URL을
순서대로 다시 돌렸더니 골든셋 점검 때와 똑같이 3건 다 본문·메타 텍스트가 완전히
비어 있었다(§ KREAM과 같은 증상). 그런데 이어서 **같은 URL 하나만** 별도 브라우저
세션으로 단순하게(5초 고정 대기 후 `document.body.innerText` 확인) 다시 열어보니
이번엔 **정상적으로 가격·상품명·리뷰까지 전부 들어 있는 완전한 페이지**가 나왔고,
727KB짜리 HTML 전체에 "Access denied"·"Error 16" 같은 문구는 어디에도 없었다.

즉 SSF샵은 **매 요청마다 일관되게 막는 게 아니다** — 같은 날 같은 방식으로도 어떨 때는
빈 페이지, 어떨 때는 완전히 정상인 페이지가 나왔다. "헤드리스 브라우저 탐지로 막는다"는
처음 판단은 재현 실패로 뒤집혔고, 지금 드는 더 합리적인 가설은 **KREAM과 같은 종류의
렌더링 타이밍 문제**(`render.py`의 대기 조건이 SSF샵 특유의 로딩 방식과 가끔 안 맞아
콘텐츠가 그려지기 전에 읽음) 쪽이다. Gemini가 빈 화면을 보고 왜 하필 "Access denied
Error 16"이라고 구체적으로 말했는지는 이걸로 설명이 안 되는데 — 빈 화면 자체에서 그런
문구를 읽어낼 리는 없으니, 스크린샷 캡처 시점에 아주 짧게 스쳐 지나가는 CDN/WAF
챌린지 화면이 있고 그게 우연히 몇 초 뒤엔 정상 콘텐츠로 바뀌는 상황일 가능성도 배제할
수 없다. 어느 쪽이든 **단발성 재현으로 "차단 문구"를 특정할 수 없었으므로
`BLOCK_PATTERNS`에 추가할 근거가 없다** — 재현 자체가 간헐적이라 다음 조사는 같은
URL을 여러 번 반복 호출해서 실패율과 타이밍(스크린샷을 여러 시점에 찍어 비교)을
먼저 확인하는 게 우선이고, 이번 조사 범위 밖이다.

## 3. 에이블리 — 기존 진단과 동일

Turnstile 차단과 동일 패턴. 안 건드림.
